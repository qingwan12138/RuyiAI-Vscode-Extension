# Provider Configuration and Streaming Chat Design

## Scope

This vertical slice completes the remaining roadmap v0.1 Foundation / Chat Vertical Slice behavior:

- configure an OpenAI cloud connection or a custom OpenAI-compatible endpoint;
- support an already-running local llama.cpp-compatible server without managing the model process;
- store API keys in VS Code SecretStorage or resolve an explicitly named environment variable;
- keep ordinary provider metadata outside secret storage;
- select a configured provider/model for the active Session and persist that binding;
- stream a real assistant response into the Webview;
- persist the final provider response after a successful stream;
- stop an active request with AbortSignal propagation;
- verify the complete chat path with fake providers and a local HTTP/SSE test server.

Agent tools, permissions beyond the existing Plan placeholder, file context, editing, and validation loops remain v0.2+ work.

## Evaluated approaches

### Selected: thin HTTP adapter over native fetch

Use a small TypeScript adapter for `/chat/completions`, `/models`, bearer authentication, response normalization, and SSE framing. This keeps Provider-specific code outside Agent Core, supports OpenAI plus compatible local servers, avoids a new runtime dependency, and allows protocol-level tests with a local server.

### Not selected: official OpenAI SDK in the shared adapter

The SDK is appropriate for an OpenAI-only product, but Yisi requires multiple providers and local compatible endpoints. Adding it now would increase dependency weight and risk leaking OpenAI-specific types across the port. A future OpenAI-specific Responses adapter can be added behind the same domain port when its capabilities are needed.

### Not selected: one generic untyped fetch function in the UI controller

This would be smaller initially but would violate the Extension Host/Webview boundary, mix persistence and transport concerns, and make cancellation, testing, and provider degradation harder.

## Official protocol basis

The implementation is based only on public protocol behavior, not copied source code:

- OpenAI documents `POST /chat/completions`, message roles, streamed chat-completion chunks, and `stream: true`: <https://developers.openai.com/api/reference/cli/resources/chat/subresources/completions>.
- OpenAI documents direct HTTP as supported, bearer authentication, and the requirement to keep API keys secret and out of client-side code: <https://developers.openai.com/api/reference/overview>.

The shared OpenAI-compatible adapter intentionally implements only the conservative common subset used by OpenAI and llama.cpp-style servers: model, text messages, streaming text deltas, HTTP errors, and cancellation.

## Architecture

```text
Webview
  -> YisiChatViewProvider (VS Code adapter)
  -> ChatService (application)
       -> SessionService
       -> ProviderCatalog port
       -> LLMProvider port
            <- OpenAICompatibleProvider (infrastructure)

Provider setup command
  -> ProviderConfigurationService
       -> ProviderConfigurationRepository port
            <- VS Code globalState/workspaceState adapter
       -> SecretStore port
            <- VS Code SecretStorage adapter
```

Domain and application modules do not import `vscode`. The Webview never receives API keys, environment-variable values, or authorization headers.

## Provider configuration model

`ProviderConfiguration` contains:

- stable `id` generated by Yisi;
- `kind: "openai" | "openaiCompatible"`;
- user-visible `name`;
- normalized `baseUrl` ending in `/v1` or another explicitly supplied compatible API root;
- `credential` as `{ source: "secretStorage" }`, `{ source: "environment"; variableName: string }`, or `{ source: "none" }`;
- known `models: string[]`;
- timestamps.

OpenAI defaults to `https://api.openai.com/v1` and requires a credential. Custom compatible endpoints accept `http` or `https`; `none` is allowed for local servers. Base URLs, provider names, model IDs, and environment-variable names are ordinary metadata. Secret values never enter configuration, session JSON, Webview state, prompts, or logs.

Configurations are global by default. Workspace state stores only an optional default provider/model override. Existing Session bindings remain authoritative; if a configuration disappears, the Session becomes unavailable rather than silently switching.

## Ports and infrastructure

`SecretStore` exposes `get`, `set`, and `delete` by opaque key. `VsCodeSecretStore` is the only module importing `vscode.SecretStorage`.

`ProviderConfigurationRepository` loads and saves a schema-versioned catalog. The VS Code adapter uses `globalState` for configurations and workspace configuration/state for the project default. Runtime parsing rejects malformed state.

`ProviderCatalog` resolves a configured provider and credential at request time. Environment credentials read only the configured variable name from an injected environment map. Missing credentials produce a normalized unavailable error without naming or logging the value.

## LLM provider contract

The current single-result `chat()` contract becomes:

```ts
interface LLMProvider {
  readonly id: string;
  listModels(signal?: AbortSignal): Promise<string[]>;
  capabilities(model: string): Promise<ModelCapabilities>;
  streamChat(request: ChatRequest, signal?: AbortSignal): AsyncIterable<ChatDelta>;
}
```

`ChatDelta` contains text only in this slice. Tool calls and usage data are deferred until the Agent Loop requires them.

`OpenAICompatibleProvider`:

- calls `<baseUrl>/models` for connection testing/model discovery;
- calls `<baseUrl>/chat/completions` with `stream: true`;
- sends `Content-Type: application/json` and bearer authentication only when a credential exists;
- parses SSE across arbitrary byte boundaries, accepts comments/blank lines, recognizes `[DONE]`, and extracts `choices[].delta.content` strings;
- treats non-2xx responses, malformed event JSON, a missing body, or an empty completed response as normalized errors;
- caps error-body text and never includes authorization data;
- propagates AbortSignal to fetch and does not convert cancellation into success.

## Chat data flow

1. The Webview sends a validated `sendMessage` request.
2. `ChatService` verifies that the active Session has an available provider/model.
3. The user message is persisted before any network request.
4. Provider input is built from persisted user messages and successful provider assistant messages. Baseline notices are excluded.
5. The host posts `assistantStreamStarted`, then sanitized text deltas.
6. The Webview renders one transient assistant item without using `innerHTML`.
7. On successful completion, `ChatService` persists one `AssistantMessage` with `source: "provider"`, then the host publishes the authoritative Session state.
8. On failure, partial text is not persisted as a completed assistant response. The user message remains durable and the UI shows a normalized error.
9. Stop aborts the active request. The Session remains available and a later user Turn can continue from persisted history.

Only one active chat run is allowed per `YisiChatViewProvider`. Sending while a run is active is rejected. The send control changes to Stop while streaming.

## Configuration and selection UI

`Yisi AI: Model Settings` opens a VS Code-native QuickPick/InputBox wizard:

1. choose OpenAI or custom OpenAI-compatible;
2. enter display name and base URL;
3. choose SecretStorage, environment variable, or no credential where permitted;
4. enter the API key only into an InputBox with password mode when SecretStorage is selected;
5. discover models or enter a model ID manually if discovery fails;
6. test the connection;
7. save only after successful validation or an explicit “Save without connection test” choice.

The composer model button lists configured provider/model pairs. Selecting one persists it to the active Session. An unavailable Session model displays an error and opens the selection flow; it is never replaced silently.

## Error and security behavior

- Webview messages continue to use exhaustive runtime validation.
- API keys are never sent to the Webview or stored in provider/session JSON.
- Environment-variable values are never displayed; only configured variable names are persisted.
- Logs contain provider ID, HTTP status, and bounded request ID when available, but not prompt text, response text, headers, or credentials.
- HTTP errors are normalized to user-safe messages.
- Connection tests use AbortSignal and a finite timeout.
- No Provider adapter may bypass future Permission Engine decisions; this slice performs chat network requests only after the user explicitly sends a message or starts a connection test.

## Testing and verification

Tests use Node's built-in runner and standard library:

- configuration schema validation and secret absence;
- configuration/default resolution and unavailable Session behavior;
- SecretStore keying with an in-memory fake;
- environment credential resolution;
- SSE framing across byte boundaries, multiple `data:` events, comments, `[DONE]`, malformed JSON, and cancellation;
- local HTTP server assertions for URL, method, JSON body, optional Authorization header, streamed response, and normalized non-2xx errors;
- fake-provider ChatService streaming, persisted final response, excluded baseline notices, failure behavior, and Stop cancellation;
- Webview protocol/state assertions for model selection and stream events;
- full `npm test`, `npm run check`, `npm run compile`, and `git diff --check`.

Real external OpenAI or llama.cpp connectivity is not required for automated tests because no credentials or server are assumed. Manual connection evidence is reported only when an endpoint is available.

## Roadmap and change checklist

1. Milestone: v0.1 Foundation / Chat Vertical Slice.
2. Responsibilities changed: provider configuration, secret adapter, LLM transport adapter, application chat orchestration, VS Code setup/selection adapter, and streaming presentation.
3. Cross-layer dependencies: no forbidden dependency is added; infrastructure implements application/domain ports.
4. Sensitive capabilities: SecretStorage, environment credential lookup, and user-triggered network requests. Tests cover redaction boundaries, authorization construction, errors, and cancellation.
5. External reference: public OpenAI HTTP behavior only; no implementation source is copied.
6. Verification evidence: unit/integration tests, typecheck, compile, diff check, and manual UI/endpoint checks when available.
7. Confirmed product decisions: unchanged.
