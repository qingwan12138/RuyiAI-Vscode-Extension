# ADR-0011 — Plan 文档化审阅（计划作为可评论的文档）

## Status
Accepted

## Decision
Plan 模式的"被审阅退出"（`request_permission`）现在可以携带一份 **markdown 计划**。当模型提交计划时：

1. 计划被渲染成一份**可编辑的 markdown 文档**在编辑器里打开（`# Plan for review` 头部 + 请求的模式 + 一行理由 + 原始计划）；
2. 文档头部写明：**在 Yisi AI 侧栏决定，本文档本身不决定任何事**；想说什么就**在文档里直接改/加**；
3. 用户决定后，**文档里被改动的内容**以 `-`/`+` 形式**作为反馈回给模型**——**批准与拒绝都回**（拒绝时附在拒绝理由里）。

### 三条边界
- **文档不是审批通道**：决定仍只发生在侧栏卡片（与 ADR-0010 同一条不变式）。文档开着不决定任何事。
- **反馈是 diff，不是整份文档**：把计划原样回传会二次消耗上下文、还让模型难以看出到底要它改什么，所以只回**用户改动的行**（复用 `renderTextDiff`），上限 2000 字符。
- **反馈是指导，不是权限**：它既不放宽也不收紧引擎的判定；批准才放宽模式，而且只对本次运行生效（既有规则不变）。

### 兼容性
`ToolConfirmationPort.confirm` 现在可以返回 `boolean | { approved, feedback? }`。**返回纯布尔值的端口照常工作**（loop 归一化两种形态），因此既有的确认端口与测试一行未改。

## Reasons
1. 能力本来就有（`request_permission` 是 Plan 的审阅出口），缺的是**让用户看清计划**：一行理由不足以判断一个多步骤改动。参考实现也是把计划打开成文档。
2. 用**未命名文档**（untitled markdown）而不是虚拟只读文档：它天然可编辑、不落盘，关闭不保存就等于"没有意见"——正好是我们要的语义，也不需要新的 provider。
3. 只回**改动行**而不是整份计划：这是上下文预算的取舍，也让"用户的意见"在会话里看得见。
4. 复用既有的批准卡片与既有的升级约束（有据可依、严格更宽、每运行一次、人来批），**没有新增任何审批入口**。

## Consequences
- 提交计划的运行会多打开一个编辑器标签；不影响卡片的决定流程。
- 未实现（明确记录，非遗漏）：把内联评论做成 VS Code 的**评论线程 API**（当前是"直接编辑文档"）；多轮计划迭代（"继续规划"）的专用 UI——目前拒绝即回到 Plan 继续工作，模型可再次提交。
- 本机未验证：VS Code 内 F5 走一遍"计划打开 → 内联加注释 → 批准/拒绝 → 模型收到反馈"的完整体验。

## Verification
`test/plan-review.test.js`（11 个）：计划的归一化与上限、文档包含审阅指引与逐字计划、**只提取被改动的行**（未改动/清空/未定义都不算反馈）、反馈有界；工具契约（可选 `plan`、空计划等同无计划）；**经真实 loop**：计划作为文档到达确认端口、**批准后注释进入工具结果**、**拒绝后注释进入拒绝理由**（且模式未被放宽）、无注释时结果与从前完全一致、**纯布尔端口仍可用**；组合根接线与"卡片仍是唯一闸门"的源码级断言。

全量：**629 tests / 628 pass / 0 fail / 1 skip**（并排 diff 那一项时为 618）。

## 开发过程中的一次真实纠错
"拒绝时反馈"的用例用 `find(denied === true)` 取拒绝消息，实际取到的是**最前面那次用于制造前置条件的策略拒绝**（`replace_text`），于是断言拿到 `policy` 而非 `user`——改为取**最后一个**拒绝。
